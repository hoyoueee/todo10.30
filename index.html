管理方式随模型架构调整

SGLang 和 vLLM 都没有为 index cache 固定一套管理方式。实际实现会随模型结构变化： DSA 采用每层 side buffer，MSA 把主 GQA 与 index K 分成两个 pool，V4 / V4.1 则按压缩率组织， 并在 V4.1 引入 source 层共享。

即便在同一引擎内，不同模型在 page 大小、entry 宽度、写入路径、source 关系和驱逐耦合上也不一样。 这些差异直接体现在 index 侧存储与主 cache 的衔接方式上。

1.1 DSA / V3.2：采用每层独立 side buffer

V3.2 的 index 侧不按压缩率或 source 组织，而是每个 DSA layer 各自一个 IndexKeyCache。它只负责该层的 index K，主 MLA cache 则由另一套 layer 管理。

存储形态

per-layer fixed slab

每层一个固定大小的 buffer，启动时按 page 一次性分配；请求来了不重新 malloc。

entry132 B
page64 entry · 8,448 B

和主 cache 的关系

page id 绑定

index page 复用主 KV 的 page id；写入位置由主 KV 的 slot_mapping 决定。

物理地址不同，但逻辑上属于同一段 token。

存储空间的计算

entry 由 128 B 的 FP8 index K 和 4 B 的 scale 组成，一共 132 B。一个 page 覆盖 64 个 token， 因此是 8,448 B。每层 buffer 的 page 数由容量向上取整，并额外留一页余量。

源码：python/sglang/srt/mem_cache/index_key_cache.py · IndexKeyCache._buffer_shape
def _buffer_shape(self, num_pages: int) -> tuple[int, int]:
    pool = self.pool
    return (
        num_pages,
        pool.page_size
        // pool.index_kpool
        * (pool.index_head_dim + pool.index_head_dim // pool.quant_block_size * 4),
    )

其中 index_kpool=1 表示一个 token 对应一个 entry；如果大于 1， 每页 entry 数按比例减少，但单个 entry 仍是 132 B。move() 只支持 index_kpool == 1，因为 pooled entry 需要重新分组。

图 1 · V3.2 的 index page 布局：K 区域和 scale 区域在同一个 page 内。

写入：index K 如何进入 cache

indexer 用独立的 W_k 从 hidden state 投影出 128 维 index K，做 LayerNorm 和部分 RoPE， 再按 128 维一个 block 量化。写入时按主 KV 的 loc 落到对应 page。 SetKAndS 同时写 K 和 scale；这个操作不经过主 attention 的 K/V。

源码：python/sglang/srt/mem_cache/index_key_cache.py · IndexKeyCache.store_quantized
def store_quantized(
    self,
    layer_id: int,
    loc: torch.Tensor,
    index_k: torch.Tensor,
    index_k_scale: torch.Tensor,
) -> None:
    buf = self._kernel_view(self.buffer[layer_id - self.pool.start_layer])
    dsa_index_k_cache.SetKAndS.execute(
        pool=self.pool,
        buf=buf,
        loc=loc,
        index_k=index_k,
        index_k_scale=index_k_scale,
    )

读取：按 page table 取 K 和 scale

indexer 打分时按 page_indices 取出 index K 和 scale，再做 paged MQA。 历史 token 的 index K 不重新计算；只有当前 query 的 index Q 是新的。

源码：python/sglang/srt/mem_cache/index_key_cache.py · IndexKeyCache.get_k_and_scale

前缀匹配与驱逐

prefix cache 仍然按 token prefix 在 RadixCache 中匹配。index 侧没有自己的树，也不额外决定命中长度； 一旦主 page 命中，它只是按同一个 page id 去读 index K。反过来，主 page 被释放后， 对应 index page 就不再有可达路径。

驱逐时只释放主 page，没有 index_cache.free()。index buffer 是固定 slab， page id 被重新分配后，下一次写入会覆盖旧数据。因此 index 不需要独立的 free queue 或 LRU。

1. 分配每层固定 slab；page 数由容量决定
→
2. 写入SetKAndS 按 loc 写 K + scale
→
3. 读取page table → GetKAndS → MQA
→
4. 驱逐主 page 释放，index page 不可达
图 2 · V3.2 的 index 生命周期完全围绕主 page。

1.2 DSA / V4.1：ratio pool 与 source 共享

V4.1 与 V3.2 的区别一方面是 entry 宽度，同时 index 侧的组织方式变了： entry 对应 compressed state，pool 按 compression ratio 建立；ratio 1/2 的 consumer 不再各自持有 K cache， 而是复用最近的 source 层。

ratio pool

按压缩率组织

每个 pool 服务一个 ratio；layer_mapping 把 layer 映射到 (ratio, compress_layer_id)。

FP8 / state132 B
FP4 / state68 B

source sharing

consumer 不新建 buffer

ratio 1/2 的 consumer 用 source_layer_of() 找到最近的 source，读它的 index K pool。

source page 释放时，所有 consumer 一起失效。

存储分配

V4.1 的 index page 有两种粒度：DeepGEMM paged sparse 时 128 个 compressed slot， 其它 backend 为 64。每个 slot 对应一个 compressed state，而不是一个原始 token。 page 字节数仍是 page_slots × bytes_per_state。

dtypeper statepage=128page=64
FP8132 B16,896 B8,448 B
FP468 B8,704 B4,352 B

例如 ratio=2、page=128 时，一个 index page 覆盖 256 个原始 token，但只有 128 个 index state。 ratio=1 时，同样 page 只覆盖 128 个 token。ratio 改变的是 entry 的语义，不只是压缩率。

源码：python/sglang/srt/mem_cache/deepseek_v4_memory_pool.py · DeepSeekV4TokenToKVPool.source_layer_of
def source_layer_of(self, layer_id: int) -> int:
    """The layer owning this layer's compressed storage: itself for ratios 4/128,
    the nearest preceding kv_source layer for ratios 1/2."""
    ratio = self.compression_ratios[layer_id]
    sources = [l for l in self.sources_by_ratio[ratio] if l <= layer_id]
    assert sources, f"layer {layer_id} (ratio {ratio}) has no kv_source layer"
    return max(sources)
图 3 · V4.1 的 source / consumer 关系：共享的是 index K pool 的所有权，不是把 consumer 合并成一层。

写入：从 compressor latent 生成 index K

V4.1 的 index K 不直接从每个原始 token 的 hidden state 算，而是从 kv-source compressor 的 latent 出发。 先做 wk 投影，再 RMSNorm、RoPE 和 FP8/FP4 量化，最后写入 index page。 因此 index K 的数量与 compressed state 对齐。

图 4 · V4.1 的写入是 latent → 投影 → norm → RoPE → 量化 → paged store；consumer 不执行这条路径。
源码路径：python/sglang/srt/layers/attention/dsv4/dsv41_sparse.py · DeepseekV41Indexer._produce_k

读取：candidate block 两级选择

V4.1 的 indexer 先在全历史 compressed position 上算 logits 的 block max，选出 candidate block； 然后只在 candidate block 内做细粒度 top-k。candidate block 是临时结果，不是持久 cache。

1. source 建池ratio 1/2 的 source 持有 index K
→
2. 写 Klatent → wk → norm → RoPE → quant
→
3. 选块block max → candidate blocks
→
4. 最终 top-k候选内做 sparse logits
图 5 · V4.1 把 index K 的组织和 top-k 的粗筛都放到 source / candidate 层。

前缀匹配与驱逐

V4.1 仍然由主 compressed page 决定 token 前缀是否可复用；index 侧没有独立 prefix tree。 source page 被释放后，consumer 的 index page 一起不可达，consumer 不能单独保留一份。 page id 复用后，source 和 consumer 看到的是新覆盖的数据。

1.3 MSA

MSA 把主 GQA K/V 与 index K 放在两个物理 pool 中。index 侧是 key-only， page 128；bf16、fp8、nvfp4 对应三套不同容量。它和 DSA 的 side buffer 不同， 这里主 cache 与 index cache 是一个组合 pool 的两个子池。

bf16

1 head × 128 dim

不做额外量化，精度最高。

entry256 B
page32 KiB

fp8

e4m3

1 B / element，容量减半。

entry128 B
page16 KiB

nvfp4

packed payload + scale

64 B payload + 8 B scale。

entry72 B
page9 KiB

写入：一个 fused kernel 同时写两套池

MSA 在 fused QKV 投影后，直接把主 K/V 和 index K 写到两个 pool。index K 走独立输出通道， 不是主 K 的复制。index page 按 128 B 行对齐，所以 nvfp4 的 9,216 B 正好落在 128 B 边界上。

图 6 · MSA 的 fused 写入：主 K/V 与 index K 来自同一个 projection，但写向两个 pool；index K 有独立输出通道。
源码路径：python/sglang/srt/models/minimax_m3.py · MiniMaxM3SparseAttention.forward

读取、前缀与驱逐

读取时 MSA indexer 从 index_k_pool 取 K，做 index score 和 block top-k； top-k 结果进入临时 buffer，不写回 cache。前缀匹配仍由主 GQA cache 的 page 决定， index pool 不参与独立匹配。主 page 释放后 index page 不可达，没有独立 index LRU/free。

1. 组合池main_pool + index_k_pool 分开分配
→
2. fused 写主 K/V 与 index K 同时落 page
→
3. index 打分读 index_k_pool，做 block top-k
→
4. 主 page 驱逐index page 跟随失效
图 7 · MSA 的两套池共享 page 生命周期，但物理存储和写入通道分开。

vLLM：layer cache + spec，采用通用 manager管理

vLLM 不把 index 做成单独的 pool 类，而是把每层 index cache 注册成通用 KVCacheSpec， 由 KVCacheManager 和 BlockPool 分配。代码里没有 DeepSeek 专用 group/component；group 和生命周期都从 spec 推导出来。

图 8 · vLLM 的“同 block”是分配层的同 block，不是同一段字节；index 仍是独立 layer page。
与 SGLang 的表达差异： SGLang 把 index cache 做成独立 pool 对象；vLLM 让模型返回 get_kv_cache_spec()，再由通用 manager 分配 block。 因此找不到 DeepSeek 专用 group/component，是正常现象。

2.1 V3.2：spec + block

V3.2 的 index cache 在 vLLM 里就是一层 layer cache。模型声明 MLAAttentionSpec(cache_role=INDEXER)：1 个 head、132 B/state、block 64。 manager 按 block 分配，runner 通过 bind_kv_cache() 绑定。

源码：vllm/model_executor/models/deepseek_v2.py · DeepseekV32IndexerCache.get_kv_cache_spec
return MLAAttentionSpec(
    block_size=self.cache_config.block_size,
    num_kv_heads=1,
    max_tp_shards=1,
    head_size=self.head_dim,
    dtype=self.dtype,
    cache_role=SparseCacheRole.INDEXER,
)  # Only has one vector instead of K + V

写入由 indexer_k_quant_and_cache 完成，位置来自主 KV 的 slot_mapping。读取用 paged MQA。block 释放时 index page 随所属 group 的 block 一起不可达；没有独立 index free/LRU。

2.2 V4：compressed state 的 spec 表达

V4 不再用“一个 token 一个 state”，而是把 tokens_per_state 设为 compress_ratio。这样同样的 block 只容纳更少的 state，但每个 state 覆盖更多原始 token。 index K 由 compressor 写，indexer 只读。

源码：vllm/models/deepseek_v4/attention.py · DeepseekV4IndexerCache.get_kv_cache_spec
return MLAAttentionSpec(
    block_size=self.cache_config.block_size,
    num_kv_heads=1,
    max_tp_shards=1,
    head_size=self.head_dim,
    dtype=self.dtype,
    tokens_per_state=self.compress_ratio,
    alignment=576 if uses_fp8_ds_mla_layout else 512,
)

V4 的 IndexCache 复用 top-k，但不改变 index K 的分配： 被跳过的层仍然保留 index page。prefix 和 eviction 仍由主 compressed block 决定。

2.3 V4.1：source sharing 与 candidate

V4.1 仍然叫 DeepseekV4IndexerCache，但只有 kv-source 真正创建 cache。 consumer 从 static_forward_context 取 source 的 cache 对象； index K 由 compressor latent 投影，top-k 使用 candidate block 两级选择。

2.4 MSA：key-only layer cache

MSA 的 MiniMaxM3IndexerCache 是 key-only layer cache，block 128。 entry 为 256 B bf16 / 128 B fp8 / 72 B nvfp4；写入仍由 fused QK-norm + RoPE + KV insert 完成， 读取由 MiniMaxM3IndexerImpl 做 index score 和 block top-k。

index page 跟随主 GQA cache 的 block。没有独立 prefix tree、LRU 或 free queue； 主 block 释放后 index page 不可达。

→
2. 分配manager 按 block 分配并绑定
→
3. 写入 / 读取量化写入，MQA 读取
→
4. 驱逐BlockPool 释放 block

每 1K token 的 index cache 占用

把不同模型的 entry 宽度归一化到 1,000 个原始 token，可以直接比较 index 侧的显存量级。 压缩模型按“每 1K 原始 token 对应多少 compressed state”换算；V4.1 的数字按一个 source layer 计， 不乘 consumer 层数。

计算口径：
entries = 1,000 / tokens_per_entry
logical_bytes = entries × entry_bytes
pages = ceil(entries / entries_per_page)
allocated_bytes = pages × page_bytes

其中 DSA / MSA 的 tokens_per_entry = 1；V4 / V4.1 的 tokens_per_entry = compress_ratio。1 KiB 按 1,024 B 计算。

1. 语义一致，表达不同。两边都把 index K 当作主 cache 的 sidecar：物理存储分开，逻辑 page/block 绑定，prefix 和驱逐跟随 owner。
